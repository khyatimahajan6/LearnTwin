Introduction to Databases

A database is a collection of related data stored in a standard format, designed to be shared
by multiple users. A database is defined as “A collection of interrelated data items that can be
processed by one or more application programs”.

A database can also be defined as “A collection of persistent data that is used by the application
systems of some given enterprise”. An enterprise can be a single individual (with a small personal
database), or a complete corporation or similar large body (with a large shared database), or
anything in between.

Example: A Bank, a Hospital, a University, a Manufacturing company

Data
Data is defined as a collection of raw, unorganized facts, observations, or symbols that serve as
the fundamental building blocks for generating useful information.
● Etymology: The term is technically the plural form of the Latin word "Datum," though in
modern computing, "Data" is commonly used in both singular and plural contexts.
● Nature: In its raw state, data lacks context and does not carry specific meaning on its
own. It represents the "input" phase of the data processing cycle.
Key Characteristics of Data
● Forms of Data: Data is versatile and can manifest in several formats, including:
○ Numeric: Numbers, integers, and floating-point values.
○ Alphanumeric: Text, characters, and strings.
○ Multimedia: Voice recordings, images, and video files.
Example: Weights, prices, costs, number of items sold etc.
Types of Data
Data can be classified based on how it is measured and how it is stored.
1. Quantitative Data (Numerical Data)
Quantitative data represents numbers and measurable values. It can be analyzed using
mathematical and statistical methods.
Types:
● Discrete Data – Whole numbers (e.g., number of students)

[Page 2]
● Continuous Data – Values within a range (e.g., height, temperature)

Age, salary, number of customers, marks, temperature.
Used in research, finance, engineering, and business analytics.
2. Qualitative Data (Categorical Data)
Qualitative data represents qualities, categories, or descriptions instead of numbers.
Customer feedback (Good/Bad), product color, gender, interview responses.
Used to understand opinions, behavior, and experiences.
3. Structured Data
Structured data is organized in rows and columns with a fixed format.
● Stored in relational databases and spreadsheets

● Easy to manage and analyze using SQL

Employee records, bank transactions, student databases.
4. Unstructured Data
Unstructured data has no predefined format and is difficult to process using traditional tools.
● Makes up the majority of global data

● Requires AI/ML tools for analysis

Emails, images, videos, social media posts, PDFs.

5. Semi-Structured Data
Semi-structured data is not fully organized like tables, but contains tags or markers that give
partial structure.

[Page 3]
● More flexible than structured data

● Easier to analyze than unstructured data

JSON files, XML files, NoSQL data, log files.

Information
Data that have been processed in such a way as to increase the knowledge of the person
who uses the data. The term data and information are closely related. Data are raw material
resources that are processed into finished information products. The information as data that
has been processed in such way that it can increase the knowledge of the person who uses
it.
In practice, the database today may contain either data or information.

Data Processing
The process of converting the facts into meaningful information is known as data processing.
Data processing is also known as information processing.

Major Drawbacks of File Processing Systems
A File Processing System stores data in separate files (like .txt or .xls) managed by
individual application programs. This approach has several critical flaws:
1. Data Redundancy and Inconsistency
● The Problem: Data is often duplicated in multiple files because different departments
create their own systems. This leads to Inconsistency, where different versions of the
same data do not match.
● Example: A student pursuing a double major in Music and Math has their phone
number stored in both department files. If they change their number and only the
Music department updates it, the Math department's record becomes incorrect.
2. Difficulty in Accessing Data
● The Problem: There is no "Search" or "Query" language. Every new request for data
requires a programmer to write a new piece of code.
● Example: A clerk needs a list of students from a specific ZIP code. If the original
programmer didn't write a "Search by ZIP" function, the clerk must either sort through
thousands of records manually or wait days for a programmer to write a new script.
3. Data Isolation
● The Problem: Data is scattered across various files in different formats (e.g., some in
C++ structures, some in COBOL, some in spreadsheets). It is nearly impossible to
write a program that pulls data from all these scattered sources at once.
● Example: Trying to create a report that links "Student Health Records" with "Library
Fines" when they are stored in two different, incompatible file formats.
4. Integrity Problems
● The Problem: "Integrity Constraints" (rules) are hard-coded into the programs. If the
rules change, you have to find and update every single program that uses that data.
● Example: A bank has a rule that an account balance cannot fall below zero. If the
bank later changes the rule to "minimum balance must be $500," the code in every
transaction program (ATM, Online, Branch) must be manually updated.
5. Atomicity Problems (The "All or Nothing" Rule)

[Page 8]
8
● The Problem: If a system crashes during a transaction, the data can be left in a
halfway state. File systems lack the "Atomic" property (where a task is either 100%
finished or 0% started).
● Example: You transfer $500 from Account A to Account B. The system crashes after
deducting from A but before adding to B. In a file system, the $500 simply
disappears.
6. Concurrent-Access Anomalies
● The Problem: When two people update the same file at the exact same time, they
may overwrite each other’s work because the system isn't coordinated.
● Example: An account has $10,000. Two clerks withdraw $500 and $100 at the same
time. Both programs read the balance as $10,000.
○ Clerk 1 writes back $9,500.
○ Clerk 2 writes back $9,900.
○ The final balance becomes $9,900 (incorrect), instead of $9,400.
7. Security Problems
● The Problem: It is difficult to restrict access to specific parts of a file. Usually, if a user
has access to a file, they can see everything in it.
● Example: An HR assistant needs access to employee names and phone numbers to
make calls, but they should not see the "Salary" column. In a simple file system,
giving them access to the file often exposes the salary data as well.
1.4 Advantages of a Database Management System (DBMS)
A DBMS offers a centralized approach to data management, solving the inherent problems
of traditional file systems. The primary benefits include:
1. Control of Data Redundancy
Unlike file systems where data is duplicated across various departments, a DBMS minimizes
Data Redundancy (repetition of data).
● Centralized Control: Managed by the Database Administrator (DBA), data is
stored in one logical place.
● Benefits: This saves significant storage space and reduces the time required for
data processing.
2. Improved Data Consistency
Data consistency is a direct result of controlling redundancy.
● When a piece of data is stored only once, any update to that data is reflected across
the entire system.
● Example: If a customer’s address is updated in a centralized database, there is no
risk of different departments holding two different addresses (disagreement of
values).

[Page 9]
9
3. Enhanced Data Integrity
Integrity refers to the accuracy and validity of the data.
● Integrity Constraints: The DBA can define specific rules that the data must follow.
● Example: A rule can be enforced so that the "City" field only accepts values like
"Noida" or "Meerut." Any attempt to enter a different city will be rejected by the
DBMS.
4. Data Sharing and Concurrent Access
A DBMS allows the same data to be shared across multiple application programs
simultaneously.
● It ensures that multiple users can access the data without interfering with one
another, supporting a collaborative environment.
5. Improved Security
Since the DBA has complete authority over the operational data, they can ensure that
access is granted only through authorized channels.
● Authorization Checks: The DBMS can perform security checks whenever a user
attempts to access sensitive information, ensuring only users with the correct
privileges can view or modify specific data.
6. Data Independence
This is one of the most critical technical advantages. The DBMS acts as an interface
between the application programs and the raw data.
● Metadata: If the physical representation of the data changes, the DBMS updates its
Metadata (description of the data structure).
● Benefit: The application programs remain unaffected by these changes, as the
DBMS handles the transformation automatically.
7. Efficient Data Access
A DBMS uses sophisticated techniques (like indexing and query optimization) to retrieve
data quickly. All access is managed through the DBMS, providing a standardized and
effective way to process large volumes of information.
8. Reduced Application Development and Maintenance Time
Because the DBMS provides many built-in functions (like searching, sorting, and security),
developers do not have to write these from scratch.
● This leads to faster development cycles and makes it easier to maintain the system
over time.

[Page 10]

Disadvantages of DBMS
1) It is bit complex. Since it supports multiple functionality to give the user the best, the
underlying software has become complex. The designers and developers should have
thorough knowledge about the software to get the most out of it.
2) Because of its complexity and functionality, it uses large amount of memory. It also needs
large memory to run efficiently.
3) DBMS system works on the centralized system, i.e.; all the users from all over the world
access this database. Hence any failure of the DBMS, will impact all the users.
4) DBMS is generalized software, i.e.; it is written work on the entire systems rather specific
one. Hence some of the application will run slow.

DBMS Architecture
o The DBMS design depends upon its architecture. The basic client/server architecture is
used to deal with a large number of PCs, web servers, database servers and other
components that are connected with networks.
o The client/server architecture consists of many PCs and a workstation which are
connected via the network.
o DBMS architecture depends upon how users are connected to the database to get their
request done.
Database Architecture Types
There are two main classifications:
1. Based on System Design

2. Based on Tiers (Client-Server Model)
Based on System Design
1. Centralized Architecture
All data and processing happen on one single server.
Advantage: Easy to manage
Disadvantage: If the server fails, the whole system stops
Example: Small office database
2. Parallel Architecture
Multiple processors work together to execute database tasks at the same time.
Advantage: Fast performance
Disadvantage: Costly and complex
Example: Large banking systems
3. Distributed Architecture
Data is stored in multiple locations connected through a network.

[Page 15]
15
Advantage: High availability
Disadvantage: Hard to maintain consistency
Example: Multinational company database
Tier-Based Architecture
Tier-based architecture explains how client and server interact.

Database architecture can be seen as a single tier or multi-tier. But logically, database
architecture is of two types like: 2-tier architecture and 3-tier architecture.

1-Tier Architecture
o In this architecture, the database is directly available to the user. It means the user can directly
sit on the DBMS and uses it.
o Any changes done here will directly be done on the database itself. It doesn't provide a handy
tool for end users.
o The 1-Tier architecture is used for development of the local application, where programmers
can directly communicate with the database for the quick response.

2-Tier Architecture
o The 2-Tier architecture is same as basic client-server. In the two-tier architecture, applications
on the client end can directly communicate with the database at the server side. For this
interaction, API's like: ODBC, JDBC are used.
o The user interfaces and application programs are run on the client-side.
o The server side is responsible to provide the functionalities like: query processing and
transaction management.
o To communicate with the DBMS, client-side application establishes a connection with the server
side.

[Page 16]
16

3-Tier Architecture

o The 3-Tier architecture contains another layer between the client and server. In this
architecture, client can't directly communicate with the server.
o The application on the client-end interacts with an application server which further
communicates with the database system.
o End user has no idea about the existence of the database beyond the application server. The
database also has no idea about any other user beyond the application. o The 3-Tier architecture
is used in case of large web application.

Data Abstraction in DBMS
Data Abstraction is the process of hiding unwanted or unnecessary details from the end user and
showing only relevant information.
It helps:
● Reduce complexity

● Improve security

● Achieve data independence
Database systems have complex data structures and relationships. To make the system easy to
use, these internal details are hidden from users using different levels of abstraction.
Levels of Data Abstraction
There are three main levels:
1. Physical (Internal) Level
Describes how data is stored in the database.
→ Includes storage details like file structure, indexing, memory blocks.
2. Logical (Conceptual) Level
Describes what data is stored and relationships between data.
→ Includes tables, attributes, and constraints.
3. View (External) Level
Describes what the user sees.
→ Only required data is shown to specific users.

Lets take real-world situation: “App should not break when DB changes”
Think about Amazon / Flipkart / Banking apps.
They keep improving their database:

If every DB change forced developers to change the application code again and again, then:
● maintenance cost becomes very high

● system becomes slow to improve

● upgrades become risky

So DBMS provides Data Independence to avoid breaking applications.

Data Independence
Data Independence is the ability of a database system to change the schema at one level
without affecting the schema at the next higher level.
It means:
● You can change how data is stored or how tables are designed

● But the application programs / user screens should not require change

👉 “Database can evolve internally, but users/apps should continue working.”
Real-world example
A college website has “Student Result” page.
If the DBA adds an index on RollNo to make search faster, the student page should work
exactly the same.
This is data independence.

Data Modeling

Data modeling is the process of creating a visual representation or a blueprint that defines the
information collection and management systems of any organization. This blueprint or data model
helps different stakeholders, like data analysts, scientists, and engineers, to create a unified view
of the organization’s data. The model outlines what data the business collects, the relationship
between different datasets, and the methods that will be used to store and analyze the data.

[Page 26]
26
Why is data modeling important?
Data modeling gives you a chance to understand your data and make the right technology choices
to store and manage this data. In the same way an architect designs a blueprint before
constructing a house, business stakeholders design a data model before they engineer database
solutions for their organization.

Data modeling brings the following benefits:
● Reduces errors in database software development
● Facilitates speed and efficiency of database design and creation
● Creates consistency in data documentation and system design across the organization
What are the types of data models?
Data modeling typically begins by representing the data conceptually and then representing it
again in the context of the chosen technologies. Analysts and stakeholders create several different
types of data models during the data design stage. The following are three main types of data
models:
Conceptual data model
Conceptual data models give a big picture view of data. They explain the following:
● What data the system contains
● Data attributes and conditions or constraints on the data
● What business rules the data relates to
● How the data is best organized
● Security and data integrity requirements
The business stakeholders and analysts typically create the conceptual model. It is a simple
diagrammatic representation that does not follow formal data modeling rules. What matters is that
it helps both technical and nontechnical stakeholders to share a common vision and agree on the
purpose, scope, and design of their data project.
Example of conceptual data models
For example, the conceptual data model for an auto dealership might show the data entities like
this:
1. A Showrooms entity that represents information about the different outlets the dealership
has
2. A Cars entity that represents the several cars the dealership currently stocks

[Page 27]
27
3. A Customers entity that represents all the customers who have made a purchase in the
dealership
4. A Sales entity that represents the information about the actual sale
5. A Salesperson entity that represents the information about all the salespeople who work for
the dealership
This conceptual model would also include business requirements, such as the following:
● Every car must belong to a specific showroom.
● Every sale must have at least one salesperson and one customer associated with it.
● Every car must have a brand name and product number.
● Every customer must provide their phone number and email address.
Conceptual models thus act as a bridge between the business rules and the underlying physical
database management system (DBMS). Conceptual data models are also called domain models.
Logical data model
Logical data models map the conceptual data classes to technical data structures. They give more
details about the data concepts and complex data relationships that were identified in the
conceptual data model, such as these:
● Data types of the various attributes (for example, string or number)
● Relationships between the data entities
● Primary attributes or key fields in the data
Data architects and analysts work together to create the logical model. They follow one of several
formal data modeling systems to create the representation. Sometimes agile teams might choose
to skip this step and move from conceptual to physical models directly. However, these models are
useful for designing large databases, called data warehouses, and for designing automatic
reporting systems.
Example of logical data models
In our auto dealership example, the logical data model would expand the conceptual model and
take a deeper look at the data classes as follows:
● The Showrooms entity has fields such as name and location as text data and a phone
number as numerical data.
● The Customers entity has a field email address with the format xxx@example.com or
xxx@example.com.yy. The field name can be no more than 100 characters long.
● The Sales entity has a customer’s name and a salesperson’s name as fields, along with the
date of sale as a date data type and the amount as a decimal data type.

[Page 28]
28
Logical models thus act as a bridge between the conceptual data model and the underlying
technology and database language that developers use to create the database. However, they are
technology agnostic, and you can implement them in any database language. Data engineers and

Types of data modeling techniques
Data modeling techniques are the different methods that you can use to create different data
models. The approaches have evolved over time as the result of innovations in database concepts
and data governance. The following are the main types of data modeling:

1. Hierarchical Data Model
The hierarchical model is one of the oldest methods of data modeling. It organizes data into a
tree-like structure, where each record has a single parent and can have multiple children.

[Page 30]
30

Key Characteristics
● One-to-Many ($1:N$) Relationship: A parent can have many children, but a child can only
have one parent.
● Root Node: The top-level record from which all other data branches out.
● Navigation: Data is accessed by traversing down from the root through the branches.
● Data Integrity: Changes to a parent record automatically cascade to its children.
Example: Auto Dealership
In this model, the Showroom is the root. It "owns" the data below it. If you delete a showroom from
the database, the associated cars and salespeople records would traditionally be deleted as well.
Advantages & Disadvantages
● Pros: Simple to understand; high performance for $1:N$ queries; clear data hierarchy.
● Cons: Inflexible; cannot represent Many-to-Many ($M:N$) relationships; leads to data
redundancy if a child needs to belong to two parents.
Network Data Model
The Network Model was a major step forward in database history, designed to overcome the
"rigidity" of the hierarchical model. While the hierarchical model restricted data to a strict tree (one
parent only), the network model allowed a record to have multiple parents, creating a graph-like
structure.
This model was formalized by the CODASYL (Conference on Data Systems Languages) Database
Task Group in 1969.

1. Key Concepts: Records and Sets
The network model is built on two fundamental building blocks:
1. Records: Similar to a "row" in a modern table or an "entity" in an ER diagram. It contains
fields of data (e.g., Student Name, ID).

[Page 31]
31
2. Sets: This represents the relationship between two record types. A set consists of:
○ Owner Record: Acts like the parent.
○ Member Record: Acts like the child.
Important: In a network model, a single record can be a "Member" in multiple different
"Sets." This is exactly how it supports many-to-many relationships.

2. Structural Features
● Graph Structure: Instead of a tree that grows downwards, the data is a web of
interconnected nodes.
● Many-to-Many ($M:N$) Support: Since a child (member) can have multiple parents
(owners), you can easily model complex real-world scenarios.
● Pointers/Links: Data is physically linked using pointers (memory addresses). To find a
record, the system "navigates" or "traverses" these links.

Advantages
● Many-to-Many Relationships: Unlike the hierarchical model, a child record can have
multiple parents.
● High Performance: Uses physical pointers (links) to move between records, making data
retrieval very fast.
● No Redundancy: You don't have to duplicate data to link it to different categories.

[Page 32]
32
● Complex Design: Managing the "web" of pointers is difficult and grows harder as the
database expands.
● Structural Dependence: If you change the database structure, you must rewrite the
application code that accesses it.
● Hard to Maintain: Inserting or deleting records requires updating many pointers, which is
prone to errors.

Relational Model in DBMS
The Relational Model organizes data using tables (relations) consisting of rows and columns.
● The relational model represents how data is stored and managed in Relational
Databases where data is organized into tables, each known as a relation.
● Each row of a table represents an entity or record and each column represents a
particular attribute of that entity.
● The relational model transforms conceptual designs from ER diagrams into
implementable structures. These structures are used in relational database systems like
Oracle SQL and MySQL.
Example: Consider a relation STUDENT with attributes ROLL_NO, NAME, ADDRESS, PHONE
and AGE shown in the table.

[Page 48]

Key Terms in the Relational Model
1. Attribute: Attributes are the properties that define an entity. For example, ROLL_NO,
NAME, ADDRESS etc.
2. Relation Schema: A relation schema defines the structure of the relation and
represents the name of the relation with its attributes. For example, STUDENT
(ROLL_NO, NAME, ADDRESS, PHONE and AGE) is the relation schema for
STUDENT. If a schema has more than 1 relation it is called Relational Schema.
3. Tuple: A Tuple represents a row in a relation. Each tuple contains a set of attribute
values that describe a particular entity. For example, (1, RAM, DELHI, 9455123451, 18)
is a tuple in the STUDENT table.
4. Relation Instance: The set of tuples of a relation at a particular instance of time is
called a relation instance. It can change whenever there is an insertion, deletion or
update in the database.
5. Degree: The number of attributes in the relation is known as the degree of the relation.
For example, The STUDENT relation has a degree of 5, as it has 5 attributes.
6. Cardinality: The number of tuples in a relation is known as cardinality . For example,
The STUDENT relation defined above has cardinality 4.

7. NULL Values: The value which is not known or unavailable is called a NULL value. It is
represented by NULL. For example, PHONE of STUDENT having ROLL_NO 4 is
NULL.
Types of Keys in the Relational Model
1. Primary Key: A Primary Key uniquely identifies each tuple in a relation. It must contain
unique values and cannot have NULL values.
2. Candidate Key: A Candidate Key is a set of attributes that can uniquely identify a tuple
in a relation.
3. Super Key: A Super Key is a set of attributes that can uniquely identify a tuple.
4. Foreign Key: A Foreign Key is an attribute in one relation that refers to the primary key
of another relation.
5. Composite Key: A Composite Key is formed by combining two or more attributes to
uniquely identify a tuple.
Characteristics of the Relational Model
● Data Representation: Data is organized in tables (relations), with rows (tuples)
representing records and columns (attributes) representing data fields.
● Atomic Values: Each attribute in a table contains atomic values, meaning no
multi-valued or nested data is allowed in a single cell.
● Unique Keys: Every table has a primary key to uniquely identify each record, ensuring
no duplicate rows.
● Attribute Domain: Each attribute has a defined domain, specifying the valid data types
and constraints for the values it can hold.
● Data Independence: The model ensures logical and physical data independence,
allowing changes in the database schema without affecting the application layer.
● Relational Operations: Supports operations like selection, projection, join, union and
intersection, enabling powerful data retrieval manipulation.
● Data
Consistency: Ensures data consistency through constraints, reducing
redundancy and anomalies.
● Set-Based Representation: Tables in the relational model are treated as sets and
operations follow mathematical set theory principles.
Constraints in Relational Model

While designing the Relational Model, we define some conditions which must hold for data present
in the database are called Constraints. These constraints are checked before performing any
operation (insertion, deletion and updation) in the database. If there is a violation of any of the

1. Domain Constraints
Domain Constraints ensure that the value of each attribute A in a tuple must be an atomic value
derived from its specified domain, dom(A). Domains are defined by the data types associated with
the attributes. Common data types include:
● Numeric types: Includes integers (short, regular and long) for whole numbers and real
numbers (float, double-precision) for decimal values, allowing precise calculations.
● Character types: Consists of fixed-length (CHAR) and variable-length (VARCHAR,
TEXT) strings for storing text data of various sizes.
● Boolean values: Stores true or false values, often used for flags or conditional checks
in databases.
● Specialized types: Includes types for date (DATE), time (TIME), timestamp
(TIMESTAMP) and money (MONEY), used for precise handling of time-related and
financial data.
2. Key Integrity
Every relation in the database should have at least one set of attributes that defines a tuple
uniquely. Those set of attributes is called keys. e.g.; ROLL_NO in STUDENT is key. No two
students can have the same roll number. So a key has two properties:
● It should be unique for all tuples.
● It can’t have NULL values.
3. Referential Integrity Constraints
When one attribute of a relation can only take values from another attribute of the same relation or
any other relation, it is called referential integrity. Let us suppose we have 2 relations

Anomalies in the Relational Model
An anomaly is an irregularity or something which deviates from the expected or normal state.
When designing databases, we identify three types of anomalies: Insert, Update, and Delete.
● Insertion Anomaly in Referencing Relation: We can’t insert a row in REFERENCING

value. e.g.; Insertion of a student with BRANCH_CODE ‘ME’ in STUDENT relation will

● Deletion/ Updation Anomaly in Referenced Relation: We can’t delete or update a

referencing relation.
Codd Rules in Relational Model
E.F. Codd, the creator of the relational model, proposed 12 rules (known as Codd’s 12 Rules) that
define what constitutes a relational database system. These rules emphasize the importance of
data independence, consistency and structure.
Key Codd’s Rules
● Rule 0: Foundation Rule: An RDBMS must manage data entirely through its relational
capabilities.
● Rule 1: Information Rule:
All data (user data and metadata) must be represented as values in table cells.
● Rule 2: Guaranteed Access Rule: Every data element is logically accessible via table
name, primary key, and column name.
● Rule 3: Systematic Treatment of NULL Values: The system must support a
representation of missing/inapplicable information that is distinct from zero or empty
strings.
● Rule 4: Dynamic Online Catalog: The database description (catalog) must be stored in
tables and queryable using the same relational language.
● Rule 5: Comprehensive Data Sublanguage Rule: The system must support at least one
language that supports data definition, view definition, data manipulation, integrity
constraints, and authorization.
● Rule 6: View Updating Rule: if a view is theoretically updatable, then the DBMS must
support update operations on that view. Simple views created from a single table
without grouping or aggregation should allow insert, update, and delete operations.
● Rule 7: High-level Insert, Update, and Delete: The system must support set-level
operations (insert, update, delete) rather than just row-by-row operations.
● Rule 8: Physical Data Independence: Changes to physical storage or access methods
do not require changes to application programs.

[Page 53]
53
● Rule 9: Logical Data Independence: Changes to the logical structure (tables) do not
require changes to application programs.
● Rule 10: Integrity Independence: Integrity constraints must be stored in the catalog, not
in application programs.
● Rule 11: Distribution Independence: The end-user should not be aware of whether the
data is centralized or distributed.
● Rule 12: Non-Subversion Rule: If the system has a low-level (record-at-a-time)
interface, it cannot be used to bypass integrity rules.
Advantages of the Relational Model
● Simple model: Relational Model is simple and easy to use in comparison to other
languages.
● Flexible: Relational Model is more flexible than any other relational model present.
● Secure: Relational Model is more secure than any other relational model.
● Data Accuracy: Data is more accurate in the relational data model.
● Data Integrity: The integrity of the data is maintained in the relational model.
● Operations can be Applied Easily: It is better to perform operations in the relational

Disadvantages of the Relational Model
● Performance: The relational model can experience performance issues with very large

● Complexity for Complex Data: The model struggles with hierarchical or complex data

● Normalization Overhead: Extensive use of normalization can result in complex queries

ACID Properties in DBMS

Transactions are fundamental operations that allow us to modify and retrieve data. However, to
ensure the integrity of a database, it is important that these transactions are executed in a way that
maintains consistency, correctness, and reliability even in case of failures / errors. This is where
the ACID properties come into play.
ACID stands for Atomicity, Consistency, Isolation, and Durability.

[Page 54]
54

These four principles are like the superheroes of data management, working together to ensure
that data is handled carefully and reliably in databases.
But why are ACID transactions important? Imagine you have an important project saved on your
computer, and suddenly, the power goes out. With ACID transactions, your project might get better,
and all your hard work could be recovered. ACID transactions come to the rescue, making sure
that even if something unexpected happens, your project remains safe and intact.
Atomicity:
Atomicity means a transaction is all-or-nothing either all its operations succeed, or none are
applied. If any part fails, the entire transaction is rolled back to keep the database consistent.
● Commit: If the transaction is successful, the changes are permanently applied.
● Abort/Rollback: If the transaction fails, any changes made during the transaction are
discarded.
Example :
Imagine you're transferring money from your savings account to your piggy bank. This transaction
involves two actions: subtracting the money from your savings account and adding it to your piggy
bank. With atomicity, both actions occur together. If, for some reason, one action fails, like if the
piggy bank is full, the entire transaction is rolled back, and the money remains in your savings
account. It's as if the transfer never happened, and you don't lose any money.

[Page 55]
55

Database Example:

Step 2: B = B + 500

👉 Step 1 is rolled back

Atomicity ensures that we don't end up with a half-finished or partially updated state. To achieve
atomicity, ACID transactions use various techniques, such as
-transactional units
Transactional units divide complex operations into smaller, manageable steps, ensuring that each
step is completed successfully before moving to the next.
-rollback,

[Page 56]
56
If any step fails, the transaction can be rolled back, undoing the changes made so far.
-recovery mechanisms.
Recovery mechanisms, like logging and undo/redo logs, help track and restore the state of the
transaction in case of failures.

2. Consistency
Consistency in transactions means that the database must remain in a valid state before and after
a transaction.
● A valid state follows all defined rules, constraints, and relationships (like primary keys,
foreign keys, etc.).
● If a transaction violates any of these rules, it is rolled back to prevent corrupt or invalid
data.
● If a transaction deducts money from one account but doesn't add it to another (in a
transfer), it violates consistency.
Imagine you have a list of friends' names, and you want to add a new name to the list. However,
there's a rule that says no two names can be the same. Consistency steps in to enforce this rule.
When you add a new name, consistency checks if it violates any rules or constraints. If the new
name is already on the list, consistency blocks the transaction, just like a superhero stopping a
villain from breaking the rules. This ensures that our data remains consistent and follows the
predefined guidelines.

- data validation

3. Isolation
Isolation ensures that transactions run independently without affecting each other. Changes made
by one transaction are not visible to others until they are committed.
It ensures that the result of concurrent transactions is the same as if they were run one after
another, preventing issues like:
● Dirty reads: reading uncommitted data
● Non-repeatable reads: data changes between two reads
● Phantom reads: new rows appear during a transaction
Imagine two individuals wanting to buy something from a store. You go to the store together, but
you each handle your transaction independently. Isolation ensures that while you are selecting your
purchase and making the payment, the other individual’s transaction is completely separate and
doesn't affect yours.

To achieve isolation, ACID transactions use techniques like
- locking
Locking is like having a special key that allows only one transaction to access a particular piece of

any interference.
- concurrency control.
Concurrency control techniques manage how transactions interact with each other. They ensure
that transactions don't step on each other's toes and that changes made by one transaction
become visible to others only when they're ready.
4. Durability:
Durability ensures that once a transaction is committed, its changes are permanently saved, even
if the system fails. The data is stored in non-volatile memory, so the database can recover to its
last committed state without losing data.
Example: After successfully transferring money from Account A to Account B, the changes are
stored on disk. Even if there is a crash immediately after the commit, the transfer details will still be
intact when the system recovers, ensuring durability.

Some useful data type for date and time are
DATE
A date. The supported range is '1000-01-01' to '9999-12-31'. MySQL displays DATE
values in 'YYYY-MM-DD' format, but permits assignment of values to DATE columns
using either strings or numbers.
DATETIME
A date and time combination. The supported range is '1000-01-01 00:00:00' to
'9999-12-31 23:59:59'. MySQL displays DATETIME values in 'YYYY-MM-DD
HH:MM:SS' format, but permits assignment of values to DATETIME columns using
either strings or numbers.
TIMESTAMP
A timestamp. The range is '1970-01-01 00:00:01' UTC to '2038-01-19 03:14:07' UTC.
TIMESTAMP values are stored as the number of seconds since the epoch ('1970-01-01
00:00:00' UTC). The value 0 is reserved for representing '0000-00-00 00:00:00', the
“zero” TIMESTAMP value.
TIME
A time. The range is '-838:59:59' to '838:59:59'. MySQL displays TIME values in
'HH:MM:SS' format, but permits assignment of values to TIME columns using either
strings or numbers.
YEAR[(2|4)]
A year in two-digit or four-digit format. The default is four-digit format. In four-digit
format, values display as 1901 to 2155, and 0000. In two-digit format, values display as
70 to 69, representing years from 1970 to 2069. MySQL displays YEAR values in YYYY
or YY format, but permits assignment of values to YEAR columns using either strings or
numbers.

Some useful data type for string
CHAR
The length of a CHAR column is fixed to the length that you declare when you create
the table. The length can be any value from 0 to 255. When CHAR values are stored,
they are right-padded with spaces to the specified length. When CHAR values are
retrieved, trailing spaces are removed. For CHAR columns, truncation of excess trailing
spaces from inserted values is performed silently regardless of the SQL mode.
VARCHAR
Values in VARCHAR columns are variable-length strings. The length can be specified
as a value from 0 to 65535. VARCHAR values are stored as a 1-byte or 2-byte length
prefix plus data. The length prefix indicates the number of bytes in the value. A column
uses one length byte if values require no more than 255 bytes, two length bytes if
values may require more than 255 bytes. For VARCHAR columns, trailing spaces in
excess of the column length are truncated prior to insertion and a warning is generated,
regardless of the SQL mode in use. The VARCHAR data type is faster than the CHAR.

BLOB
A BLOB is a binary large object that can hold a variable amount of data. BLOB values
are treated as binary strings (byte strings). There is no padding on insert and no bytes
are stripped on select.
TEXT
A TEXT is a binary large object that can hold a variable amount of data. TEXT values
are treated as nonbinary strings (character strings). There is no padding on insert and
no bytes are stripped on select.
BLOB and TEXT columns cannot have DEFAULT values.
ENUM
An ENUM is a string object with a value chosen from a list of permitted values that are
enumerated explicitly in the column specification at table creation time.
The ENUM type has these advantages:
1. Compact data storage in situations where a column has a limited set of possible
values. The strings you specify as input values are automatically encoded as
numbers.
2. Readable queries and output. The numbers are translated back to the
corresponding strings in query results.

1. Not Null
The null refers to the missing value, absence of value or using null is required when the
value is not applicable. null is different from 0 (zero). Let us come to the not null constraint.
A. It ensures that the column must have the value i.e. it cannot have null value
B. This constraint is applicable for columns only
C. A table can have any number of columns with NOT NULL constraints
e.g. empname and salary both columns are with not null constraints

2. Primary Key
A. Used to uniquely identify a record in the table
B. Duplicate values & null is not allowed
C. In a table we can have at most one primary key yet it is possible to create a table
without a primary key.
D. A primary key can be made from a single column (i.e. simple primary key) or it can be
made from combination of multiple columns (i.e. composite primary key).
e.g. in the above table, the empid column is working as the primary key. It is an example of

3. Unique Key
A. Only Unique values are allowed in the column with unique constraint but null is also
allowed such that null can be inserted any number of times.
B. A table can have any number of unique keys

A. It is used to define the default value for the column such that default value will be

e.g. Every applicant in a government exam is considered of unreserved category by default.
To take advantage of reservation, a cast certificate is required. So unreserved is the default
value.
e.g. salary with some minimum value can be provided as default value

5. Foreign Key
A reference to a primary or unique key in another table. It is used to define relationships
between one or more tables. The table which is referenced by the foreign key is called
parent/Master/Primary table and the foreign key containing column is called child
table/slave table/Secondary table.

Foreign Key comes with referential integrity constraint; what does it means-
1. A foreign key column can have value either from the referencing columns or it can have
null. Duplicate values are also allowed in the Foreign key column.
2. When a record from the parent table is deleted then all referencing entries in the child
table will be either deleted or they should be having value null.
3. The column names for the primary key and foreign key are not required to be the same
but their data types must be the same.

The Foreign Key has following properties
The foreign key column can have null value, all other values will be from the referenced
column. If any entry from the parent table is going to be deleted then make sure no
corresponding entry should be there in the secondary table. To maintain the same we use
"ON DELETE" strategy that has following-
A. Set NULL: If any entry from the parent table is being deleted then all corresponding
entries in the child table will be set as null
B. Cascade: If any entry from the parent table is being deleted then all corresponding
entries in the child table will be deleted

Note: When a column is applied with foreign key constraint then it is implicitly made an
index by MySql for efficient look-up.

6. Check
The CHECK constraint in MySQL is used to ensure that a column’s value meets a specific
condition but in many versions of MySQL (especially before v8.0.16), CHECK constraints
are parsed but not enforced.

SQL (Structured Query Language)
To give instruction to the DBMS, we have to use SQL. SQL is cross platform, open source, ANSI
standard computer language that is the same for all the databases. SQL is case Insensitive, you
may use any case. By convention all keywords must be in capital and the query should be properly
aligned.

Types of SQL
1. DDL (Data Definition Language)
A. Used to create, alter, modify the structure of the database
B. It never deals with the data that is stored in the table
e.g. CREATE, ALTER & DROP

2. DML (Data Manipulation Language)
A. Used to insert/update and delete the records from the table
B. It never deals with the structure of database and table
e.g. INSERT, UPDATE & DELETE

3. DRL (Data Retrieval language)
A. It is used to fetch/read/retrieve records from the table
e.g. SELECT

4. DCL (Data Control Language)
A. Used to define permissions/privileges for the database
e.g. GRANT, REVOKE

5. TCL (Transaction Control Language)
A. They are used to control the transaction which refers to a set of queries that is to be
treated as a whole means either the complete set of queries should be executed or all
the queries should be rolled back.
e.g. COMMIT, ROLLBACK, START TRANSACTION, SAVEPOINT

Group By: The main purpose of the group by clause is to group the records/rows logically.
1. All non-aggregate columns of the SELECT clause must be mentioned in the GROUP
BY clause such that GROUP BY clause can have any additional non-aggregate
2. If the select list contains the non-aggregate and aggregate columns then use of
GROUP BY is mandatory.
3. You must not use aggregate functions with GROUP BY, use column name(s) only.
4. You must not use column aliases with the GROUP BY because the SELECT clause
is executed after GROUP BY so aliased names are not available at the time of
execution of the GROUP BY.
5. The group by clause can be used for more than one column also.
6. You can use WHERE clause with GROUP BY clause but WHERE clause is used to
apply filter condition row wise means first records will be filtered using WHERE
condition and then GROUP will be made from the results after executing WHERE. In
short; WHERE clause does not apply condition on the result of GROUP BY it applies
condition of every record one by one.

The Cartesian Product (×), also known as the cross-product, is a fundamental binary

Definition
The Cartesian Product of two relations R and S (R × S) produces a relation that contains
all possible combinations of tuples from relation R and relation S.
Each tuple in the resulting relation is formed by concatenating a tuple from R with a tuple
from S.

What is a View in DBMS?

[Page 145]
145
A View is a virtual table based on the result-set of an SQL statement. Unlike a real table, a
view does not contain data of its own; it dynamically pulls data from one or more underlying
"base tables" whenever it is queried.

Why Do We Need Views? (Key Advantages)
1. Data Security and Privacy
This is the most critical reason. Views allow you to restrict access to sensitive data.
● Example: In an Employees table, you can create a view that shows names and
departments to the HR team, but hides sensitive columns like Salary or SSN.
2. Simplifying Complex Queries
If a database has a complex structure involving multiple joins, subqueries, and filters, writing
that query repeatedly is prone to error.
● The Solution: You can hide the complexity behind a view. Students can then run a
simple SELECT * FROM view_name instead of a 20-line SQL join.
3. Logical Data Independence
Views provide a layer of abstraction between the database and the user application.
● The Benefit: If the underlying table structure changes (e.g., a column is renamed or
a table is split into two), you can simply update the View definition. The end-users or
applications using the view won't even notice the change.
4. Customization for Different Users
Different users have different needs.
● A Sales Manager needs to see revenue data.
● A Warehouse Manager needs to see stock levels.
● Instead of creating new tables, you create different views on the same base data to
suit each role's perspective.
5. Consistency
By using a view, you ensure that all users are seeing the same "version of the truth." If a
specific calculation (like "Total Profit") is defined within a view, every department using that
view will get the same result, preventing calculation errors across different reports.

Functional Dependency

A constraint between two sets of attributes in a relation is known as functional dependency.
It is denoted as X→Y, where:
● X is the determinant, and
● Y is the dependent attribute.
According to this notation, two rows in a table must have the same value for X if they also have the
same value for Y. In simpler words, the value of X determines the value of Y.
Functional dependency is represented by an arrow sign (→) that is, X→Y, where X functionally
determines Y.
Example: Consider a table with table name Students:

Here, StudentID uniquely determines the Name and Department. This can be represented as:
● StudentID → Name
● StudentID → Department

[Page 151]
151
Functional dependency is commonly used in database architecture and normalisation and is vital
for ensuring data consistency.
Types of Functional Dependency
1. Full Functional Dependency:
When every attribute in the determinant is required to determine the dependent attribute, the
functional dependency is said to be complete. The reliance would be broken if the determinant's
attributes were removed.
Example: Consider a table with the table name Course:

Here, CourseID → Instructor and CourseID → Duration are full functional dependencies, as
CourseID alone determines both Instructor and Duration.
2. Partial Functional Dependency:
If an attribute is determined by only a part of a composite key, the dependency is said to be partial.
Example: Consider a table Subject:

[Page 152]
152
{CourseID, SubjectID} → SubjectName is a composite key dependency, but SubjectID →
SubjectName is a partial dependency as SubjectID alone determines SubjectName.
3. Transitive Dependency:
When an attribute indirectly depends on the determinant through another attribute, this is known
as a transitive dependency.
Here, EmployeeID → DepartmentID and DepartmentID → DepartmentName, implying
EmployeeID → DepartmentName is a transitive dependency.
Higher stages of normalisation deal with transitive dependencies, which frequently make data
linkages more difficult.
What is Normalization?
Normalization is the process of structuring data and the attributes of a database to store the data
logically and avoid redundancy. Data redundancy refers to the same data stored in several places
in a database. In normalization, larger tables are divided into smaller ones and linked using
relationships. To eliminate redundancy, we use various normal forms in DBMS.
Purpose of Normalization
Data redundancy in database management systems leads to anomalies that make it hard to
manage the database. Normalization is necessary to remove these anomalies and bring more
consistency to the database.

Insertion Anomaly

ACID Properties in DBMS
A transaction is a single logical unit of work which accesses and possibly modifies the contents of

— Abort: If a transaction aborts, changes made to database are not visible.
— Commit: If a transaction commits, changes made are visible.

Different Types of Transaction States in DBMS

These are the different types of Transaction States:
1. Active State
2. Partially Committed State
3. Committed State
4. Failed State
5. Aborted State
6. Terminated State
1. Active State
● It is the first stage of any transaction when it has begun to execute. The execution of
the transaction takes place in this state.
● Operations such as insertion, deletion, or updation are performed during this state.
● During this state, the data records are under manipulation and they are not saved to
the database, rather they remain somewhere in a buffer in the main memory.
2. Partially Committed

[Page 174]
174
● The transaction has finished its final operation, but the changes are still not saved to
the database.
● After completing all read and write operations, the modifications are initially stored in
main memory or a local buffer. If the changes are made permanent in the database
then the state will change to "committed state" and in case of failure it will go to the
"failed state".
3. Committed
This state of transaction is achieved when all the transaction-related operations have been
executed successfully along with the Commit operation, i.e. data is saved into the database after
the required manipulations in this state. This marks the successful completion of a transaction.
4. Failed State
If any of the transaction-related operations cause an error during the active or partially committed
state, further execution of the transaction is stopped and it is brought into a failed state. Here, the
database recovery system makes sure that the database is in a consistent state.
5. Aborted State
If a transaction reaches the failed state due to a failed check, the database recovery system will
attempt to restore it to a consistent state. If recovery is not possible, the transaction is either rolled
back or cancelled to ensure the database remains consistent.
In the aborted state, the DBMS recovery system performs one of two actions:
● Kill the transaction: The system terminates the transaction to prevent it from affecting
other operations.
● Restart the transaction: After making necessary adjustments, the system reverts the
transaction to an active state and attempts to continue its execution.
6. Terminated State
It refers to the final state of a transaction, indicating that it has completed its execution. Once a
transaction reaches this state, it has either been successfully committed or aborted. In this state,
no further actions are required from the transaction, as the database is now stable.

Example of Transaction States

[Page 175]
175

Imagine a bank transaction where a user wants to transfer $500 from Account A to Account B.
The system should handle the following transaction states:
Active State
● The transaction begins. It reads the balance of Account A and checks if it has enough
funds.
● Example: Read balance of Account A = $1000.
Partially Committed State
● The transaction performs all its operations but hasn’t yet saved (committed) the
changes to the database.
● Example: Deduct $500 from Account A's balance ($1000 - $500 = $500) and
temporarily update Account B's balance (add $500).
Committed State
● The transaction successfully completes, and the changes are saved permanently in the
database.
● Example: Account A’s new balance = $500; Account B’s new balance = $1500.
Changes are written to the database.
Failed State
● If something goes wrong during the transaction (e.g., power failure, system crash), the
transaction moves to this state.
● Example: System crashes after deducting $500 from Account A but before adding it to
Account B.
Aborted State
● The failed transaction is rolled back, and the database is restored to its original state.
● Example: Account A's balance is restored to $1000, and no changes are made to
Account B.

[Page 176]
176
These states ensure that either the transaction completes successfully (committed) or the
database is restored to its original state (aborted), maintaining consistency and preventing errors.

Schedule in DBMS
Scheduling is the technique of preserving the order of the operations from one transaction to
another while executing such concurrent transactions. A series of operations from one transaction
to another transaction is known as a schedule.
What is Scheduling, and why is it required?
Transactions are a set of instructions that perform operations on databases. When multiple
transactions are running concurrently, then a sequence is needed in which the operations are to
be performed because at a time, only one operation can be performed on the database. This
sequence of operations is known as Schedule, and this process is known as Scheduling.
When multiple transactions execute simultaneously in an unmanageable manner, then it might
lead to several problems, which are known as concurrency problems. In order to overcome these
problems, scheduling is required.
Types of Schedules
There are mainly two types of scheduling -
1. Serial Schedule
2. Non-serial Schedule Further, they are divided into their subcategories, as shown below.

[Page 177]

Serial Schedules-

In serial schedules,
● All the transactions execute serially one after the other.
● When one transaction executes, no other transaction is allowed to execute.
Characteristics-
Serial schedules are always-
Consistent: Since transactions execute fully and in isolation, the database always moves from
one valid state to another without violating any rules.
Recoverable:If a transaction reads data written by another transaction, then the transaction that
wrote the data must commit first before the reading transaction commits. Since transactions run
one after another in serial schedules, this condition is always satisfied.

[Page 178]
178
Cascadeless: No transaction ever reads uncommitted (dirty) data from another, so the failure of
one transaction never forces others to abort.
Strict: No transaction is allowed to read or write a data item until the previous transaction that
modified it has fully committed or aborted.

View Equivalent Schedules-

Consider two schedules S1 and S2 each consisting of two transactions T1 and T2.
Schedules S1 and S2 are called view equivalent if the following three conditions hold true for
them-

Condition-01:

For each data item X, if transaction Ti reads X from the database initially in schedule S1, then in
schedule S2 also, Ti must perform the initial read of X from the database.
“Initial readers must be same for all the data items”.
Condition-02:

[Page 193]
193
If transaction Ti reads a data item that has been updated by the transaction Tj in schedule S1,
then in schedule S2 also, transaction Ti must read the same data item that has been updated by
the transaction Tj.
“Write-read sequence must be same.”.

What is concurrency control in DBMS?

A transaction is a single reasonable unit of work that can retrieve or may change the data of a
database. Executing each transaction individually increases the waiting time for the other
transactions and the overall execution also gets delayed. Hence, to increase the throughput and to
reduce the waiting time, transactions are executed concurrently.
Example: Suppose, between two railway stations, A and B, 5 trains have to travel, if all the trains
are set in a row and only one train is allowed to move from station A to B and others have to wait
for the first train to reach its destination then it will take a lot of time for all the trains to travel from
station A to B. To reduce time all the trains should be allowed to move concurrently from station A
to B ensuring no risk of collision between them.
When several transactions execute simultaneously, then there is a risk of violation of the data
integrity of several databases. Concurrency Control in DBMS is a procedure of managing
simultaneous transactions ensuring their atomicity, isolation, consistency and serializability.

Need of Concurrency Control
Concurrency control is essential to:

● Prevent conflicts between simultaneous transactions.
● Maintain data consistency and accuracy in multi-user environments.
● Avoid problems such as dirty reads, lost updates and inconsistent reads.

[Page 201]
201
Concurrency Problems in Transactions

Before understanding isolation levels, it is essential to understand the three fundamental problems
that arise when transactions execute concurrently without adequate isolation. These problems
occur because one transaction may read or modify data that another transaction is also working
with.

1) Dirty Read

Definition: A dirty read occurs when a transaction reads data that has been modified by another
transaction but has not yet been committed. If the modifying transaction is rolled back, the data
read by the first transaction becomes invalid, as it never officially existed in the database.

2) Non-Repeatable Read

Definition: A non-repeatable read occurs when a transaction reads the same row twice and gets
different values each time, because another committed transaction modified the data between the
two reads

3) Phantom Read

[Page 202]
202

Definition: A phantom read occurs when a transaction re-executes a query and finds that the result
set has changed because another committed transaction inserted or deleted rows that match the
query's search condition.

Transaction Isolation Levels

Transaction isolation levels define how concurrent transactions interact to maintain data
consistency and integrity. As part of the ACID properties, isolation ensures each transaction acts
independently. The four levels, Read Uncommitted, Read Committed, Repeatable Read, and
Serializable, balance performance and data accuracy.

Transaction Isolation Levels define how much one transaction can see the changes made by
other concurrent transactions.

Why Do Databases Offer Different Isolation Levels?

Databases offer different isolation levels because there is a trade-off between consistency and
performance.
Higher isolation gives more accuracy but slower performance, while lower isolation gives better
performance but may cause data errors.

[Page 203]
203

The four standard isolation levels are:
1. Read Uncommitted
This is the lowest level of isolation where a transaction can see uncommitted changes made by
other transactions. This can result in dirty reads, non-repeatable reads, and phantom reads.

Typical Use Cases: Approximate analytics, trend analysis, rough data exploration, and
scenarios where speed is prioritized over accuracy.
2. Read Committed
In this isolation level, a transaction can only see changes made by other committed transactions.
This eliminates dirty reads but can still result in non-repeatable reads and phantom reads.

[Page 204]
204

Typical Use Cases: Web applications, e-commerce platforms, content management systems,
and most general-purpose applications where moderate consistency is acceptable.

3. Repeatable Read
This isolation level guarantees that a transaction will see the same data throughout its duration,
even if other transactions commit changes to the data. However, phantom reads are still possible.

Typical Use Cases: Reporting systems, dashboards, and scenarios where row-level consistency
is required but the exact count of rows in range queries is less critical.

4. Serializable
This is the highest isolation level where a transaction is executed as if it were the only transaction
in the system. All transactions must be executed sequentially, which ensures that there are no dirty
reads, non-repeatable reads, or phantom reads.

[Page 205]
205

Typical Use Cases: Banking and financial systems, critical inventory management, any scenario
where absolute data correctness is non-negotiable.
Setting Isolation Levels in SQL

The SQL standard provides a SET TRANSACTION statement to explicitly specify the
isolation level for a transaction. The syntax is straightforward:
-- Highest isolation: complete serial execution
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Row values are stable across reads within a transaction
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Only committed data is visible (most common default)
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- No isolation: uncommitted data is visible
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

[Page 206]
206
The SET TRANSACTION statement applies to the next transaction only. In most database
systems, you can also set the isolation level for an entire session using SET SESSION or
database-specific syntax. For example, in MySQL you can use SET SESSION TRANSACTION
ISOLATION LEVEL followed by the desired level.

Locks in DBMS
What is a Lock in DBMS?
A lock in DBMS is a mechanism that controls concurrent access to data items in the database.
It allows only one transaction (or limited transactions) to use a data item at a time, depending
on the type of lock.
This ensures:
● Data integrity (data remains correct)
● Consistency (no wrong updates)
● Prevention of concurrency problems such as:
○ Lost Update
○ Dirty Read
Lock-Based Protocols in DBMS
Lock-Based Protocols are rules that ensure a transaction cannot read or write data until it
obtains the required lock on that data item.
🔹 How Lock-Based Protocols Work
1️⃣ Before accessing any data item, a transaction must request a lock.
2️⃣ If the lock is available,it is granted to the transaction.
3️⃣ If the lock is not available,the transaction must wait until the lock is released.
4️⃣ After completing its operation, the transaction releases the lock.

Types of Lock

[Page 207]
207

1) Shared Lock (S): Shared Lock is also known as Read-only lock. As the name suggests it can
be shared between transactions because while holding this lock the transaction does not have the
permission to update data on the data item. S-lock is requested using lock-S instruction.
2) Exclusive Lock (X): Data item can be both read as well as written. This is Exclusive and
cannot be held simultaneously on the same data item. X-lock is requested using lock-X instruction.
Rules of Locking
The basic rules for Locking are given below:
Read Lock (or) Shared Lock(S)
● If a Transaction has a Read lock on a data item, it can read the item but not update it.
● If a transaction has a Read lock on the data item, other transaction can obtain Read
Lock on the data item but no Write Locks.
● So, the Read Lock is also called a Shared Lock.
Write Lock (or) Exclusive Lock (X)
● If a transaction has a write Lock on a data item, it can both read and update the data
item.
● If a transaction has a write Lock on the data item, then other transactions cannot obtain
either a Read lock or write lock on the data item.
● So, the Write Lock is also known as Exclusive Lock.

The Two-Phase Locking (2PL) Protocol

The Two-Phase Locking protocol is a concurrency control protocol that guarantees serializability. It
requires that each transaction issue lock and unlock requests in two distinct phases:
Growing Phase: A transaction may obtain locks but may not release any lock. During this phase,
the transaction acquires all the locks it needs.
Locking rule: “You can lock doors, but cannot unlock any yet.”

Shrinking Phase: A transaction may release locks but may not obtain any new locks. Once the first
lock is released, the transaction enters this phase.

Locking rule: “You can unlock doors, but cannot lock new doors.”

[Page 209]
209
The point in the schedule where the transaction has obtained its final lock is called the lock point.
Transactions can be serialized according to their lock points.

Variants of Two-Phase Locking

1 Basic Two-Phase Locking

In basic 2PL, locks can be released as soon as they are no longer needed, as long as no new
locks are acquired afterward. This can lead to cascading aborts.
If the first transaction fails or is rolled back, the second transaction that used its data may also
become invalid.
This can cause a chain reaction of rollbacks, which is called a cascading abort.
2 Strict Two-Phase Locking
Strict 2PL requires that all exclusive locks taken by a transaction be held until the transaction
commits or aborts. This prevents cascading aborts and ensures recoverability.

Rule: Hold all X-locks until commit/abort

Benefit: Prevents dirty reads and cascading aborts

Usage: Most commonly used in practice

3 Rigorous Two-Phase Locking

Rigorous 2PL requires that ALL locks (both shared and exclusive) be held until the
transaction commits or aborts.

Rule: Hold ALL locks until commit/abort

Benefit: Simplifies transaction management and recovery

Drawback: Reduces concurrency compared to strict 2PL

write(A);
unlock(A); // Shrinking phase starts
lock-X(B); // VIOLATION! Cannot acquire lock in shrinking phase

This transaction violates 2PL because it tries to acquire a lock on B after releasing the
lock on A.

lock-X(B); // Still growing
read(A); // Lock point reached

write(A);
read(B);
B := B + 50;
write(B);
unlock(A); // Shrinking phase
unlock(B);

Deadlock in DBMS
A deadlock occurs in a multi-user database environment when two or more transactions block
each other indefinitely by each holding a resource the other needs. This results in a cycle of
dependencies (circular wait) where no transaction can proceed.

For Example: Consider the image below

In the above image, we can see that:
● T1 locks Resource "Student" and needs Resource "Grade"
● T2 locks Resource "Grade" and needs Resource "Student"
● T1 waits for T2, T2 waits for T1, hence resulting in a deadlock
Necessary Conditions for Deadlock to Occur

[Page 212]
212
There are four necessary conditions that must be met for a deadlock to occur in a DBMS.
These conditions were stated by Coffman. A Deadlock in DBMS will occur if all of the four
condition holds true at any point in time. The conditions are:
● Mutual Exclusion: At least one resource must be held in a non-shareable mode,
meaning only one process can access it at a time.
● Hold and Wait: A process is holding at least one resource and is waiting for
additional resources that are currently held by other processes.
● No Preemption Condition: Resources cannot be taken away from a process and
given to another process.
● Circular Wait: A set of processes are waiting for resources held by each other,
forming a circular chain.
When all four conditions are met, a deadlock occurs, and the processes involved are unable
to proceed or release their resources. This results in a situation where the system cannot
continue processing transactions.
Why Deadlocks Are a Problem?

● Transactions are stuck indefinitely.
● System throughput decreases as transactions remain blocked.
● Resources are held unnecessarily, preventing other operations.
● Can lead to performance bottlenecks or even system-wide standstill if not
handled.
Real-Life Example
Transaction T1:
● Locks rows in Students
● Wants to update rows in Grades
Transaction T2:

[Page 213]
213
● Locks rows in Grades
● Wants to update rows in Students
Both wait on each other and this results in deadlock, and all database activity comes to a
standstill.
How to Handle Deadlocks
There are some approaches and by ensuring them, we can handle deadlocks. They are discussed
below:
1. Deadlock Avoidance
Plan transactions in a way that prevents deadlock from occurring.
Methods:
● Access resources in the same order. For e.g., always access Students first, then
Grades
● Use row-level locking and READ COMMITTED isolation level. It reduces chances, but
doesn’t eliminate deadlocks.completely

2. Deadlock Detection
If a transaction waits too long, the DBMS checks if it’s part of a deadlock.

Method: Wait-For Graph
● Nodes: Transactions
● Edges: Waiting relationships
● If there’s a cycle, a deadlock exists. It's mostly suitable for small to medium databases

[Page 214]
214

3. Deadlock Prevention
For a large database, the deadlock prevention method is suitable. A deadlock can be prevented if
the resources are allocated in such a way that a deadlock never occurs. The DBMS analyzes the
operations whether they can create a deadlock situation or not, If they do, that transaction is never
allowed to be executed.
Deadlock prevention mechanism proposes two schemes:
1. Wait-Die Scheme (Non-preemptive)
● Older transactions are allowed to wait.
● Younger transactions are killed (aborted and restarted) if they request a resource held
by an older one
● Consider two transaction- T1 = 10 and T2 = 20
● If T1 (older) wants a resource held by T2 → T1 waits
● If T2 (younger) wants a resource held by T1 → T2 dies and restarts
Prevents deadlock by not allowing a younger transaction to wait and form
a wait cycle.
2. Wound-Wait Scheme (Preemptive)

[Page 215]
215
● Older transactions are aggressive (preemptive) and can force younger ones to abort.
● Younger transactions must wait if they want a resource held by an older one.
● Consider two transaction- T1 = 10 and T2 = 20
● If T1 (older) wants a resource held by T2 → T2 is killed, T1 proceeds.
● If T2 (younger) wants a resource held by T1 → T2 waits
Prevents deadlock by not allowing younger transactions to block older ones.

Deadlock Recovery
When a system detects a deadlock, it must take immediate action to break the cycle and return to
a functional state. This is typically achieved through recovery strategies or by implementing strict
concurrency controls to prevent the situation from occurring in the first place.
1. Deadlock Recovery Strategies
Once a deadlock is identified, the system must resolve it by selecting a victim transaction to roll
back and eventually restart.
Victim Selection Criteria

[Page 216]
216
To minimize the impact on system performance and fairness, the system evaluates:
● Work Progress: How much work has the transaction already completed?
● Resource Usage: How many data items/resources is it currently holding?
● Cascading Impact: How many other transactions will be affected by this rollback?
● Starvation Avoidance: How many times has this specific transaction been rolled back
before? (Prevents a single process from being perpetually targeted).
A. Killing the Process (Termination)
This is the most "aggressive" approach to clearing a deadlock.
● Methods: Abort All: Terminate every process involved in the deadlock cycle.
○ Stepwise Abort: Terminate processes one by one until the cycle is broken.
● Mechanism: Killing a process forces it to release all held resources, breaking the Circular
Wait condition.
● Downsides: Loss of unsaved data and wasted computational effort/time.
B. Process Rollback
Instead of total termination, the system reverts the process to a known "healthy" state.
● Mechanism: Uses Checkpointing (regularly saving the process state). When a deadlock
occurs, the process is reset to the last safe checkpoint.
● Downsides: High overhead; frequent state-saving consumes significant memory and CPU
cycles.
C. Resource Preemption
The system forcibly takes a resource from one process and reassigns it to another.
● Mechanism: The "preempted" process is placed in a waiting state until its required
resource becomes available again.
● Downsides: Starvation. If the same process is always the one losing its resources, it may
never complete its task.

Multiple Granularity Locking in DBMS
Granularity refers to the size of the data item on which a lock is applied. Multiple Granularity

● File: groups of records
● Record: individual data entries
A transaction can lock any node, and doing so implicitly locks all of its descendants.

How It Works
● If a transaction locks a file in exclusive (X) mode, it implicitly holds an exclusive

● This differs from traditional tree locking because you don’t have to lock each child

Intention Lock Modes
To support multiple granularities efficiently, we introduce intention lock modes:
❖ IS (Intention-Shared): Intention to obtain S locks at finer granularity. It means the
transaction wants to get Shared (S) locks on some lower-level items.
❖ IX (Intention-Exclusive): Intention to obtain X locks at finer granularity. It means the
transaction wants to get Exclusive (X) locks on some lower-level items.
❖ SIX (Shared + Intention-Exclusive): Holds S lock on current node and intends X locks
below.

Multiple-Granularity Locking Protocol
Rules for acquiring locks:

1. Lock the root first (in any mode)

2. Can lock node Q in S or IS mode only if parent is locked in IX or IS mode

3. Can lock node Q in X, SIX, or IX mode only if parent is locked in IX or SIX mode

4. Locks are acquired in top-down (root-to-leaf) order

5. Locks are released in bottom-up (leaf-to-root) order

Timestamp based Concurrency Control

Timestamp-based concurrency control is a technique used in database management systems
(DBMS) to ensure serializability of transactions without using locks. It uses timestamps to
determine the order of transaction execution and ensures that conflicting operations follow a
consistent order.
Each transaction T is assigned a unique timestamp TS(T) when it enters the system. This
timestamp determines the transaction’s place in the execution order.
Timestamp Assignment Methods
System Clock: TS = current system time
T1 starts at 10:30:05.123 → TS(T1) = 10:30:05.123
T2 starts at 10:30:07.500 → TS(T2) = 10:30:07.500
Since 05.123 is earlier than 07.500 → T1 is older than T2.

Logical Counter: TS = counter value (incremented for each transaction)
T1 enters → TS = 1
T2 enters → TS = 2
T3 enters → TS = 3
Numbers tell the order → smaller number = older transaction.

[Page 221]
221
Property: If Ti enters system before Tj, then TS(Ti) < TS(Tj)

Data Item Timestamps
Each data item Q has two timestamps:
W-timestamp(Q): Largest timestamp of any transaction that executed write(Q) successfully
R-timestamp(Q): Largest timestamp of any transaction that executed read(Q) successfully.

Timestamp-Ordering Protocol Rules

For read(Q) by transaction Ti:

If TS(Ti) < W-timestamp(Q): Reject and rollback Ti (reading wrong value)

If TS(Ti) ≥ W-timestamp(Q): Execute read and set R-timestamp(Q) = max(R-timestamp(Q),
TS(Ti))

For write(Q) by transaction Ti:
If TS(Ti) < R-timestamp(Q): Reject and rollback Ti (value already read by newer
transaction)

If TS(Ti) < W-timestamp(Q): Reject and rollback Ti (writing obsolete value)
Otherwise: Execute write and set W-timestamp(Q) = TS(Ti)

Example 1: Timestamp Ordering Execution

Consider transactions T1, T2, T3 with TS(T1)=1, TS(T2)=2, TS(T3)=3:
Initial: R-timestamp(X) = 0, W-timestamp(X) = 0
T1: read(X)
Check: TS(T1)=1 ≥ W-timestamp(X)=0 → OK
Execute: R-timestamp(X) = 1
T3: write(X)
Check: TS(T3)=3 ≥ R-timestamp(X)=1 → OK
Check: TS(T3)=3 ≥ W-timestamp(X)=0 → OK
Execute: W-timestamp(X) = 3
T2: write(X)
Check: TS(T2)=2 ≥ R-timestamp(X)=1 → OK
Check: TS(T2)=2 < W-timestamp(X)=3 → FAIL!

Result: T2 is rolled back (obsolete write)

What is database backup and recovery?
Database backup and recovery techniques refer to the process of making copies of your

Difference between backup and recovery
Data backup and recovery are two sides of the same coin, but they serve very different

utilities, or cloud storage services. The goal is to preserve data in a safe, restorable state.
Recovery is more reactive. It kicks in after a problem like a crash, corruption, or accidental
deletion occurs, using a backup to restore systems to a functional state. Recovery tools and
processes include rollbacks, rollforwards, point-in-time restores, and full system restores.

● Prevents downtime

A full database backup creates a complete copy of your entire database. It’s thorough and
straightforward but also time-consuming and storage-heavy. While full backups are great for
clean restore points, you’ll likely rack up quite the cloud bill if you create them all the time.
All student records copied every Sunday.
Incremental database backup
Incremental backups only save data that changed since the last backup of any type. This
makes them fast, lightweight, and ideal for frequent backup schedules. It’s the same
principle as iCloud only backing up your new photos rather than your entire camera roll. The
downside of incremental backups is that recovery means painstakingly stitching together
multiple smaller files.
Monday: full backup
Tuesday: only new records saved

[Page 226]
226
Differential database backup
Differential backups record everything that changed since the last full backup. They take up
more space than incremental backups, but it’s quicker to action a recovery, since you only
need two files: the last full and the last differential. It’s a happy medium for teams that want
efficiency without complex restore chains.

Monday changes saved
Tuesday saves Monday + Tuesday changes

Recovery in DBMS
A Database Management System must protect data from failures such as system crashes, power
failures, software errors, or hardware faults. During transaction execution, some changes may be
completed while others may remain incomplete. If failure occurs in the middle of execution, the
database can enter an inconsistent state.
To bring the database back to a correct and consistent state, the DBMS uses recovery
techniques. Two important concepts used in recovery are:
● Log-based recovery
● Checkpoint mechanism
These techniques help the DBMS recover committed transactions and undo incomplete
transactions.
1. Log-Based Recovery

Introduction
Log-based recovery is a recovery method in which the DBMS keeps a record of all transaction
activities in a special file called the log.

[Page 227]
227
The log stores information about:
● start of a transaction
● read and write operations
● old values of data items
● new values of data items
● commit of transaction
● abort of transaction
This log is used after a failure to determine:
● which transactions should be redone
● which transactions should be undone
Thus, log-based recovery is one of the most important techniques for maintaining database
consistency.
Typical log records are:
● <Ti start>
● <Ti, X, old_value, new_value>
● <Ti commit>
● <Ti abort>
Where:
● Ti = transaction identifier
● X = data item modified
● old_value = value before update
● new_value = value after update

Write-Ahead Logging (WAL)
An important rule in log-based recovery is Write-Ahead Logging.
Rule:
The log record must be written to stable storage before the actual data item is written to the
database.
This means:
● first update is recorded in log
● then actual database page is updated
This ensures that even if failure occurs after writing the log but before writing the data, the system
can still recover.

[Page 228]
228
Types of Log-Based Recovery
There are mainly two approaches:
● Deferred database modification
● Immediate database modification
1. Deferred Database Modification
In deferred modification, the actual database is not updated until the transaction reaches
its commit point.
The updates are recorded only in the log during execution. After the transaction commits, the
changes are applied to the database.
This approach is also called No-Undo/Redo in some contexts.

How it Works
1. Transaction starts
2. Update operations are recorded in the log
3. Actual database is not changed immediately
4. If transaction commits, updates are applied to database
5. If system crashes before commit, no database change was made, so no undo is
required
6. If crash occurs after commit but before all updates are written, redo may be needed

Suppose transaction T1 transfers money.
Log records:
● <T1 start>
● <T1, A, 5000, 4000>
● <T1, B, 3000, 4000>
● <T1 commit>
If crash occurs before commit:
● database not updated yet
● no undo needed
If crash occurs after commit but before data is fully written:

[Page 229]
229
● redo T1
Advantages of Deferred Modification
● simpler recovery logic
● no need to undo uncommitted transactions
● safer because database is updated only after commit
● updates are delayed
● may reduce speed in some systems
● committed results may not appear immediately
Immediate Database Modification

In immediate modification, the database can be updated before the transaction commits.
This means changes may reach the database while the transaction is still active.
Hence, if failure occurs, the system may need:
● undo for uncommitted transactions
● redo for committed transactions
This is why immediate modification is often called Undo/Redo based recovery.
How it Works
1. Transaction starts
2. Log records are written before data is updated
3. Database may be updated before commit
4. If transaction commits and crash occurs, redo may be needed
5. If transaction does not commit and crash occurs, undo is needed
Transaction T2 updates account balance.
Log:
● <T2 start>
● <T2, A, 1000, 800>
● <T2, B, 2000, 2200>
Suppose the system crashes before <T2 commit>
Then:

[Page 230]
230
● database may already contain partial updates
● since transaction did not commit, these updates must be undone
Suppose crash occurs after commit:
● committed updates may need redo if not fully saved
Advantages of Immediate Modification
● allows faster buffer and page handling
● suitable for practical database systems
● more flexible
● recovery is more complex
● both undo and redo may be needed
● partial updates may exist in database before commit

Using the Log to Redo and Undo Transactions

Redo and Undo Procedures

[Page 231]
231
redo(Ti): Sets the value of all data items updated by Ti to the NEW values from the log
records.
undo(Ti): Restores the value of all data items updated by Ti to the OLD values. Also writes
redo-only log records and finally a <Ti abort> record.

Recovery Decision Rules
Undo Ti if: The log contains <Ti start> but does NOT contain <Ti commit> or <Ti abort>.
Redo Ti if: The log contains <Ti start> AND either <Ti commit> or <Ti abort>.

2. Checkpoints
A checkpoint is a mark point where all previous logs are saved permanently to the storage disk.
The log files before the checkpoint can be removed, and the updated data is stored safely on
disk.
When a checkpoint occurs, all updates are written to the database, and unnecessary old logs
are cleared.

Without Checkpoint

If a system failure occurs:

● This makes recovery slow and time-consuming.

● T4 starts just before failure
● Then system failure occurs
After failure:

Demerits of Without Checkpoint

Entire log file needs to be searched.
2. Redoing Unnecessary Transactions
Old transactions are checked again even if they were safe.

● Collect checkpoint data in stable storage.

Database Security

A database is one of the most valuable assets of any organization because it stores
important information such as customer records, employee details, financial data, medical history,
examination results, business transactions, and confidential reports. Since databases contain
sensitive and critical information, they must be protected from unauthorized access, accidental
damage, and malicious attacks.
Database security refers to the set of measures, policies, tools, and techniques used to protect a
database against threats and to ensure that the data remains safe, accurate, available, and
confidential.
Database security is not only about preventing outsiders from accessing data. It also includes
protecting the database from internal misuse, hardware failures, software errors, and human
mistakes.

Database Security Concepts
Database security is built on some fundamental concepts. These concepts define what needs to
be protected and how protection should be provided.
1.1 Confidentiality
Confidentiality means that data should be accessible only to authorized users and should remain
hidden from unauthorized persons.
● A student should not be able to view another student’s marks.
● An employee should not be able to see payroll records of all employees unless permitted.
● Medical records should be visible only to authorized doctors and hospital staff.
Confidentiality is maintained through:
● passwords
● authentication
● authorization
● encryption
● access control mechanisms
If confidentiality is broken, sensitive information may be leaked, stolen, or misused.

1.2 Integrity

[Page 237]
237
Integrity means that data in the database should remain correct, consistent, and trustworthy.
It ensures that:
● unauthorized users cannot modify data
● data is not changed accidentally
● database rules and constraints are maintained
● updates are performed correctly
● A bank account balance should not change incorrectly.
● A student’s roll number should not be duplicated.
● Marks should remain within a valid range.
Integrity can be preserved using:
● constraints
● validation rules
● transaction control
● concurrency control
● authorization rules
● backup and recovery methods
If integrity is lost, the database may contain wrong, inconsistent, or corrupted data.

1.3 Availability
Availability means that authorized users should be able to access the database whenever needed.
A secure database should not only protect data from intruders, but also ensure that the data is
available for normal use.
● ATM databases must be available all the time.
● Hospital records should be accessible during emergencies.
● College result systems should be available during result announcements.
Availability is affected by:

● username and password
● OTP
● smart cards
● biometric methods

Distributed Database System in DBMS
In the most basic terms, a distributed database is a database that stores data in multiple locations
instead of one location. This means that rather than putting all data on one server or on one
computer, data is placed on multiple servers or in a cluster of computers consisting of individual
nodes. These nodes are oftentimes geographically separate and may be physical computers or
virtual machines within a cloud database.
Introduction to Distributed Database System in
A distributed database is a database system that spans multiple computers or nodes that are
connected by a network. Each node in a distributed database can store a portion of the data, and
the entire database is made up of the sum of the data stored on each node.
In a distributed database, data is stored and processed in a distributed manner, and the system
ensures that the data remains consistent and available to users despite network failures or other
system errors. The primary goal of a distributed database is to provide high availability, scalability,
and performance to applications that require access to large amounts of data.
Need of Distributed Database In Dbms
Let's start with the databases and their types,
● A database is an structured collection of information. The data can be easily accessed,
managed, modified, updated, controlled, and organized in a database.
● Databases can be broadly classified into two types, namely Distributed and Centralized
databases. The question here is why do we even need a Distributed Database In Dbms?.
Let's assume for a moment that we have only centralized databases.
○ We will be inserting all the data into one single database. Making it too large so that
it will take a lot of time to query a single piece of record.
○ Once a fault occurs, we no longer be able to serve user requests as we have only
one database.

[Page 254]

○ No scaling is possible even if we wanted to and availability is also less which in turn

Distributed databases resolve various issues, such as availability, fault tolerance, throughput,
latency, scalability, and many other problems that can arise from using a single machine and a
single database. That's why we need distributed databases. Let's discuss them in detail.
Distributed Databases
● A distributed database is a database that is not limited to one computer system. It is like a
database that consists of two or more files located in different computers or sites either on
the same network or on an entirely different network.
● These sites do not share any physical component. Distributed databases are needed when
a particular data in the database needs to be accessed by various users globally. It needs
to be handled in such a way that for a user it always looks like one single database.

Replication
● As the name suggests, the system stores copies of data at different sites. If an entire

Advantages of Distributed Database In Dbms
1. Better Reliability: Distributed databases offers better reliability than centralized databases.
When database failure occurs in a centralized database, the system comes to a complete
stop. But in the case of distributed databases, the system functions even when a failure
occurs, only performance-related issues occur which are negotiable.
2. Modular Development: It implies that the system can be expanded by adding new
computers and local data to the new site and connecting them to the distributed system
without interruption.
3. Lower Communication Cost: Locally storing data reduces communication costs for data
manipulation in distributed databases. In centralized databases, local storage is not
possible.
4. Better Response Time: As the data is distributed efficiently in distributed databases, this
provides a better response time when user queries are met locally. While in the case of
centralized databases, all of the queries have to pass through the central machine which
increases response time.
Disadvantages of Distributed Database In Dbms
1. Costly Software: Maintaining a distributed database is costly because we need to ensure
data transparency, coordination across multiple sites which requires costly software.
2. Large Overhead: Many operations on multiple sites require complex and numerous
calculations, causing a lot of processing overhead.
3. Improper Data Distribution: If data is not properly distributed across different sites, then
responsiveness to user requests is affected. This in turn increases the response time.

CAP Theorem says that a distributed system can guarantee only two
out of these three at the same time:

● C – Consistency: every user sees the same latest data
● A – Availability: every request gets a response
● P – Partition Tolerance: system keeps working even if network failure happens
between servers
Since network partition can happen in distributed systems, usually the real choice is
between:
● CP: Consistency + Partition Tolerance
Example: Banking system
If one server cannot confirm the latest balance, it may refuse the transaction to avoid
wrong data.
● AP: Availability + Partition Tolerance
Example: Social media / DNS
System gives a response even if some users may see slightly old data.
Simple example:
Suppose two servers store your account balance. If the network link breaks:
● If system chooses Consistency, one server may stop replying until data matches
● If system chooses Availability, both servers reply, but one may show old balance
So, CAP theorem means during a network partition, you must choose either
consistency or availability, not both.

Introduction to NoSQL

NoSQL stands for "Not Only SQL".
It refers to a class of non-relational databases designed to store and manage large volumes of
unstructured or semi-structured data.

Instead of the typical tabular structure of a relational database, NoSQL databases, house data
within one data structure, such as JSON document. Since this non-relational database design
does not require a schema, it offers rapid scalability to manage large and typically unstructured
data sets.
NoSQL is also type of distributed database, which means that information is copied and stored on
various servers, which can be remote or local. This ensures availability and reliability of data. If
some of the data goes offline, the rest of the database can continue to run.
Today, companies need to manage large data volumes at high speeds with the ability to scale up
quickly to run modern web applications in nearly every industry. In this era of growth within
cloud, big data, and mobile and web applications, NoSQL databases provide that speed and
scalability, making it a popular choice for their performance and ease of use.

Why NoSQL Was Introduced (Need for NoSQL)
Traditional relational databases (RDBMS) like MySQL, Oracle Database, and Microsoft SQL
Server work well for structured data.
However, modern applications generate:
● Huge volumes of data
● Different types of data (text, video, images, logs)
● Fast-changing data
● Real-time data streams
Relational databases faced limitations such as:
Problems with Traditional RDBMS

[Page 265]
265
1. Rigid Schema
○ Table structure must be defined in advance.
○ Difficult to change later.
2. Limited Scalability
○ Mostly vertical scaling (adding more power to one server).
○ Expensive.
3. Performance Issues
○ Slow with very large datasets.
4. Handling Unstructured Data
○ Not efficient for JSON, media files, logs.

How does NoSQL work?
NoSQL features are unique to the database you choose. However, they typically share several
similar high-level qualities:
● They follow flexible schemas that don’t require you to determine or declare a fixed schema
for your data, making them ideal for semi-structured and unstructured data
● They scale horizontally, using range or hash distributions, instead of having to depend on
vertical scaling to add capacity
● They’re optimized for specific data models and workload patterns, such as key-value,
wide-column, or in-memory
● They often exhibit consistency at some later point (for example, eventual consistency
model) rather than following the stricter ACID (atomicity, consistency, isolation, durability)
properties of relational and SQL databases
● They usually don't support cross-shard transactions or flexible isolation modes
These features make non-relational databases ideal for applications that require large scale,
reliability, high availability, and frequent data changes.
Types of NoSQL Databases

Databases manage data efficiently, and NoSQL systems provide scalable and flexible solutions for
modern applications handling diverse data.
● Relational databases use structured tables.
● NoSQL supports unstructured and semi-structured data.
● Built for scalability and modern workloads.

NoSQL Database Types

NoSQL databases can be classified into four main types, based on their data storage and retrieval
methods:

1. Key-Value Stores
The simplest NoSQL model. Data is stored as a dictionary of unique keys mapped to opaque
values. The database treats the value as a blob and does not interpret its structure.

2 Document-Based Stores
Stores data in structured documents (JSON, BSON, XML). Each document is self-describing and
can contain nested arrays and sub-documents. Documents in the same collection can have
entirely different fields (flexible schema).

3 Column-Family (Wide-Column) Stores
Organizes data into column families rather than rows. Each row can have a different set of
columns. Data is stored column-by-column on disk, making it extremely efficient for analytical
queries that read specific columns across millions of rows.

Explicitly designed to store and navigate relationships. Data is modeled as nodes (entities) and
edges (relationships connecting them). Both nodes and edges can have properties. Optimized for
traversal queries like finding shortest paths or friends-of-friends.

What is MongoDB?
MongoDB is a document database designed to help developers build modern applications faster. It
stores data in flexible, JSON-like documents, making it easy to model data the same way your
application code uses it. The flexible schema lets you evolve your data model without downtime,
iterate quickly, and easily handle non-uniform data.
MongoDB provides a powerful query engine, horizontal scaling, and built-in high availability so you
can support everything from rapid prototyping to large, mission-critical workloads.

MongoDB Architecture
The architecture of MongoDB is designed to handle high availability and massive horizontal
scaling through the following four core components:
1. Replica Sets
● Definition: A group of MongoDB servers (typically 3 or more) that maintain the exact same
dataset.
● Roles:
○ Primary Node: The single point of contact that handles all write operations.
○ Secondary Nodes: These nodes replicate data from the primary to ensure
redundancy.
● Fault Tolerance: If the primary node fails, the system automatically holds an election to
promote a secondary node to be the new primary, ensuring zero or minimal downtime.
2. Sharding
● Definition: The process of dividing a large dataset into smaller, manageable "chunks."
● Distribution: These chunks are distributed across multiple servers, known as shards.
● Mechanism: Distribution is managed based on a specific field called a shard key.

[Page 271]
271
● Goal: Provides horizontal scalability, allowing the database to handle massive datasets
that exceed the storage or processing limits of a single server.
3. Mongos Router
● Function: Acts as the interface or "query router" in a sharded cluster.
● Operation: It intercepts client queries and determines exactly which shard (or shards)
contains the requested data.
● Routing: It uses the shard key to direct traffic to the correct location, making the sharding
process transparent to the user.
4. Config Servers
● Role: These servers act as the "brain" or the directory of the sharded cluster.
● Data Stored: They store the metadata for the cluster, including:
○ The mapping of which data lives on which specific shard.
○ The boundaries of data "chunks."
○ Overall cluster configuration settings.

10. Projection
Projection is used to control which fields are returned in query results. Instead of fetching the
entire document, you can include or exclude specific fields. This improves performance when
documents have many fields.

Include Specific Fields (1 = include)
db.students.find({}, { name: 1, branch: 1 })
// Returns only name and branch fields (+ _id by default)

Exclude Specific Fields (0 = exclude)
db.students.find({}, { marks: 0, age: 0 })

db.students.find({}, { name: 1, branch: 1, _id: 0 })

always be explicitly excluded alongside include projections.

12. Indexing
An index is a special data structure that stores a small portion of a collection's data set in an
easy-to-traverse form. Indexes improve the speed of query operations significantly. Without
an index, MongoDB performs a collection scan — reading every document.

Default Index on _id
MongoDB automatically creates a unique index on the _id field for every collection. You
cannot remove this index.

Create an Index — createIndex()
// Single field index (ascending)
db.students.createIndex({ name: 1 })

// Single field index (descending)
db.students.createIndex({ marks: -1 })

// Compound index (multiple fields)
db.students.createIndex({ branch: 1, marks: -1 })

// Unique index (no duplicate values allowed)
db.students.createIndex({ email: 1 }, { unique: true })

View All Indexes
db.students.getIndexes()

Drop an Index
db.students.dropIndex({ name: 1 })

// Drop all indexes except _id
